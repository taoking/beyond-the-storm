# 05｜目标美术、结构原型与正式游戏资产：三层定义与协作边界

> **2026-11-13，GPT 美术设计交接记录。** 用户已明确：喜欢的雪夜木屋图是希望最终达到的**视觉品质/氛围方向**；当前 SVG / Canvas 不好看，是因为它们主要用于验证构图、状态、镜头和图层技术。**这不代表最终美术允许保持低保真，也不表示目标图已经是可运行素材。** 本文件把三个概念分开，避免 GPT 与 Claude 使用同一个「高保真完成」表述造成误解。

## 1. 三种东西不是一回事

| 产物 | 简称 | 应回答什么 | 绝不宣称什么 |
|---|---|---|---|
| 用户认可的雪夜木屋效果图与本轮无 HUD 的 LOOKDEV 参考 | **TARGET / 目标美术** | 《风雪之外》最终该有怎样的温暖、孤寂、细节和人物生活感 | 不等于实际游戏截图、不等于拆分好的透明图层，也不等于图中所有物件已获设计批准 |
| 04 v1.4 交互 HTML、05 v0.3–v0.6 SVG/Canvas 和镜头导出流水线 | **PROTOTYPE / 结构原型** | 场景空间、三个镜头、真实尺寸、状态可视化、图层可导出是否可行 | **不是**目标美术完成度的证明；v0.6 的「真实 Chromium 截图通过」仅是工程渲染与文件完整性 |
| 下一阶段按同一风格重绘并能独立驱动的背景/角色/天气/炉火等 | **PRODUCTION / 可运行美术资产** | 真实高品质、多状态、可拆分、可复用，能与 Claude 06 的事实数据一对一对应 | 不把整张 AI 效果图或设计板截图放进去充当多状态动画，也不让视觉层发明世界事件 |

**项目对外描述**：05 v0.7 进入「目标美术与制作规范明确、开始高品质视觉试片」阶段；**未进入正式美术完成阶段**。后续报告至少同时说明：视觉品质 / 分层可用度 / 真机验收 / 实际世界接入四个维度，不能只用一个百分比。

## 2. 目标图采纳什么，不采纳什么

**采纳的视觉品质**：
- 大雪窗与远山/松林的寒蓝，室内木墙与炉火的琥珀橙，冷暖交界柔和但像素颗粒清晰；
- 书桌在雪窗下，人物自然读书/写观测记录，窗台/桌面有能让人回访时辨认的小东西；
- 有生活痕迹：真实有来源的书、旧观测记录、已有收音机、煤油仪器暖炉、煤炉茶壶、柴堆；细节自然，不用巨量 UI 证明系统很丰富；
- 像素层次清楚：远景、室内梁柱、木纹、家具、人物和炉火各有景深与光照关系，不让文字遮挡画面。

**不自动采纳的内容**：
- 图上大的左右侧栏、体力/温饱/情绪进度条、资源清单、世界日的密集数值、满屏任务面板；
- 图里可能生成的猫、额外设备、背包位置、植物品种、尚未修复的设施、太阳/时间轴等。**每个可变化的物件必须先核对 02/03**；未获批准的只能留在 LOOKDEV 参考中；
- 角色一直坐在窗下、每次打开都在读书、每天都有新记录或自动追踪人物。角色行为由 Claude 06 的实际逻辑决定，允许空镜和等待；
- 把视觉效果图中的「五帧炉火」「四帧动作」「28 层」等美术板描述当成真实已验收数量；实际能复用的帧/层必须逐文件列清，缺的写「待生产」。

## 3. 可执行的美术落地路线（按门槛，不按画图次数）

### Gate A：单张无 HUD 的正式美术方向试片

至少有一张**纯场景图**，同屏包含雪窗/窗下人物/炉火，没有侧栏/生存进度条/字幕/宠物。其色彩、人物比例、细节、室内外材质接近用户认可的目标图。**此阶段可以用 AI 完整图做效果对齐；它仍叫 LOOKDEV，不能叫拆分完成。**

本轮已制作一个不含 HUD 的 1024×576 构图参考和不同局部取景：它是从 v0.7 生成设计板中**裁切**出来的单张画面，非独立重绘的 clean plate；没有 GitHub 二进制文件写入能力，因此以本对话附件 ZIP 提供，GitHub 只存本文件、接口清单与来源说明。

### Gate B：一套真正有质量的**可生产**木屋母场景

需要以 Gate A 为视觉锚点**重新绘制/整理高保真可编辑源图**，把「静态背景 clean plate（无人、无状态火焰）」与「真实可变对象」分开。
- 独立窗外（天空/远山/近松/雪粒/天气与时段变化，窗口严格遮罩）；
- 静态建筑/家具（木材纹理、窗框、桌面、书架、炉体、院门）；
- 可变生活物件（茶杯/翻开的书、玻璃罐填充、柴堆档位、修缮阶段及实际已有的陈设）；
- 灯光/炉火（真实五态与暖区，光照可以叠层但不能穿透墙面、也不能在火灭时保持旺火）；
- 人物与服装/动作（室内毛衣便服，屋外才穿帽子围巾；同一主角轮廓/比例/脸形保持一致）。

**验收**：拆层→重组后与目标纯场景**视觉接近**，真正达到「不是色块原型」的状态；不能只检验 RGBA 数值差异很小——低保真图一样能做到像素级重组。

### Gate C：用正式品质素材验证小窗

真实 320×180、480×270 与 1280×720 的**整个窗口**渲染，按 04 默认小窗雪窗／可选炉边、完整窗全景；人物在/不在时都合理，桌前人物头肩和手部可读、雪景不是只剩半扇窗。

- 05 v0.6 的候选裁切属于技术基准；Gate B 高品质素材完成后必须**重新验收**，不能沿用旧色块场景的裁切坐标硬塞。
- 用实际桌面工作的无鼠标状态观察 320 小窗，UI 不抢焦点；A2 一轮结束小结/A3 近况卡必须仍能看清但不盖住人物。
- 先看观感，再决定是否需要新的逻辑像素密度；不牺牲角色可读性去机械追求 1×/2× 整数缩放。

### Gate D：真实世界接入，不能靠导演按钮伪造

Claude 06 负责真实世界、计时、人物日程、事件和存档。GPT 提供图层/姿态/镜头/遮挡关系，双方共同评审适配。只让**真实事实源**控制场景，禁止演示按钮生成新存档事件。

**最小联调矩阵**：人物在窗下读书、去泉屋窗下空镜、人物在炉边、熄火/余烬/正常火、日夜和降雪、现实专注记录先增加但球果罐等人物整理后才更新、户外临时专注冻结但人物依然在外。

## 4. 先停下来的事

在 Gate B 真正通过前，不批量铺三张完整远行地图、四季全量版本、24 件样式图、猫狗与新设施；不继续把 SVG 几何体贴满细节然后称「高清精修」；不因为 Claude 灰盒尚未就绪而私自新建另一套游戏世界系统。

## 5. 双方下一次同步需要什么

| GPT 交付 | Claude 交付 | 用户要看的 |
|---|---|---|
| 一份明确的视觉质量目标、纯场景参考、静态/动态/条件性图层清单及实际窗景样本 | 角色真实位置/动作/日程的只读事实字段与世界时钟/炉火/天气的有限状态，是否已存在相应事件 | 高品质无 HUD 的木屋和 320/480 真实尺寸效果，并非 28 张层名列表 |
| 资产的命名、透明度、锚点、动画与减动态效果要求 | 状态值到展示字段的建议适配层、数据是否可暂停/恢复、实际角色出现率 | 同一个人物、同一房间能随真实世界生活 |
| 清楚注明未完成的动画和特殊天气 | 确认先接最小场景，不为了视觉改已定稿奖励/生态与人物自主规律 | 可运行画面优先于华丽的假活动 |

**结论**：用户喜欢的是 *TARGET*，现在 GitHub v0.6 较丑的是 *PROTOTYPE*；中间缺的是 *PRODUCTION* 美术制作，而不是再跑十轮 SVG 导出测试。
