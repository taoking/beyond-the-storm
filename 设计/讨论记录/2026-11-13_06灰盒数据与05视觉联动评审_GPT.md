## 一、结论先行：06 已经给出视觉真正需要的事实源

Claude 已交付纯 TypeScript 世界模拟、现实专注、四状态和薄 UI；报告中 **93 条测试／类型检查／构建通过**，300×8 世界年长跑断火/缺餐均为 0。这些是 **Claude 提供的测试记录，GPT 此次核查的是代码和报告，未独立运行其整个测试矩阵**。

重要的是 `game/src/core/view.ts` 的 **`present(g,wall,cal): Snapshot`**：它已经集中提供 `mode`、`frozen`、`world`、`actor`、`stage`、`fire`、`life`、`stock`、`projects`、`jar`、`today`、`traces`、`focus`。而 `scene.ts` 明确只是 960×270 的位置方块示意（屋内在 x=0–480），**不是 05 最终的 480×270 木屋母场景**。这使 G2 可以采取单向数据流：

```
06 world/focus deterministic state
             ↓
     present() : Snapshot
             ↓
G2 readonly presentation adapter
     ├─ scene location anchors + camera coverage
     ├─ actual time / weather / season, ambient presentation override

     ├─ fireplace flame + light tiers
```

**不得**由渲染器构造新的角色事件、给额外份数、修改存档，亦不得因某个镜头里没人就改变 02 自主作息。

## 二、需要纠正的 A1/A4 预期：不应该承诺「小窗常常有人」

`40 seeds × 60 world days`，正常陪伴、不出门、不专注，**总游戏时间 345.6 万分钟，清醒时间 2319331 分钟**，由 `game/src/core/cameras.ts` 的「地点是否在镜头候选集合」计量（不是逐像素遮挡）。

| 镜头 | 清醒时可见 | 全世界时间可见 | 解读 |
|---|---:|---:|---|
| 雪窗（window/windowsill/desk） | **18.8%** | 12.6% | 日常有人只占一部分，不是常驻人物 |
| 炉边（hearth/armchair/stove/instruments） | **43.7%** | 29.3% | 取决于吃饭和做饭的物件真实空间位置 |
| 完整屋内 | **78.3%** | 52.5% | 真实清醒时间多数在屋内 |
| 屋内＋院子 | **87.2%** | 58.5% | 相比屋内全景理论只多 **8.9 个百分点** |

说明：

1. **U5 已确认小窗默认雪窗**、U2 已确认不自动追踪；不因数据擅自改成炉边默认，也不在人物不在桌边时暗中自动切镜。空景是本游戏的一部分。
2. 雪窗只有 18.8% 不否定 A1：雪窗、桌面与人物动作同镜头依旧有必要，但设计应称「**回访时能看见生活痕迹，偶尔遇见他在窗下**」，不能承诺「大多数时间能看见人」。
3. **真正影响下一轮母图的空间布局是扶手椅 26.4% 清醒时间、灶台 12.5%、书桌 13.7%、雪窗 5.1%**。此前概念参考图非常突出窗边桌和火炉，但**扶手椅/做饭区位置不清楚**；如果不在艺术布局中把它们安排合理，所谓炉边 43.7% 就只是报告里的地点假设。
4. 可探索把扶手椅放在**窗下书桌与炉区之间、略偏炉边的共同可见地带**，让窗景保留生活感、炉边镜头也能看见自然坐姿；**前提是同一母场景真实相邻，且角色矩形能被对应裁切容纳**。这需要新的无 HUD 美术母图上的物理坐标和真实裁切验证，**不能把书桌与扶手椅硬合并为一个位置**，也不能凭这一摆位把窗景可见率算作 45%。
5. **不要为 8.9 个百分点直接把所有全景横向拉大**：如果加入院子导致大雪窗/人物/炉火变小，全景品质反而下降。A4 继续作为「室内＋真实院门侧翼」候选，先用视觉样片和灰盒地点分布判定是否值得。场景若真的只画屋内，则明示「78.3%」而非沿用旧的 87%。
6. 所有比例只在**现有默认行为和当前拍摄区域假设**下成立；真实户外、不同修缮阶段、用户改项目优先级或早睡请求会改变分布。05 应给每个作品单独定义可视位置表，复跑 `node tools/report.ts --runs 40 --days 60`（在 `game/` 内），并最终以真实像素 actor bbox∩camera crop 可见百分比验证，避免位置集合预测夸大视觉结果。

### 进一步的体验解读

**现实 2 小时平均 0.7 条「值得一提」的世界事件，10% 的时间窗是 0 条；同时约 17.1 次日常动作变化。** 因此：

- 04 A3 的「看看今天」**不能要求凑齐四条重要新事**；真实大事少时显示 1 条或 0 条，再以带时间的**真实平常事**（提水、吃饭、读书、翻页、整理）补充，不伪造阶段完成或日记剧情。
- 回访的第一层来自雪/时段/真实炉火/手头动作和桌面痕迹，第二层才是近况卡，第三层才是长手记；不要把 17.1 次活动变化强制变成 17 条弹窗。
- `Snapshot.today.top` 现按权重排前四再按时间排序，`more` 取接下来两条，足够作为**事实来源**；正式 UI 仍需区分「今天的小事」与「重要变化」，并处理新的一天尚无事件时的空态。
- 默认雪窗中无人时，以风雪、窗台罐子、书、杯、桌灯及**真实去向短句**承接安静感。为保证看见人而添假人影或额外动效，会破坏游戏体验。

## 四、G2 交接：已有 Snapshot 足以做第一条真连接，存在两处表现层差异

已核对 `game/src/core/view.ts`：

- `Snapshot.stage` 含 `show/place/label/illusion`，**渲染人物应优先按 stage 决定**；`Snapshot.actor` 是真实状态，提供 `place/outfit/asleep/whereabouts/visible`。氛围态下 stage 可以是演出，不得反写 world。
- `Snapshot.fire.look` 已有五态 `out/ember/low/mid/high`；这是制作 P0 火焰与光照精灵的接口，不需要设计第二个火焰模拟器。
- `Snapshot.world.look/dayPart`、`jar.cones/pending`、`traces`、`projects`、`today` 都能驱动视觉表现；雪窗天气必须受真正场景遮罩限制。
- **候选差异 1**：`present()` 的 `actor.visible` 由真实 `actor.place` 计算，但独立氛围态的 `stage.place` 可能固定为 `armchair`，所以预览用角色的可见性与原世界人物可见标志会不同。建议 G2 从 `stage.place` 与 camera bbox 计算“画出来是否可见”，把 `actor.visible` 留作现实信息；**不要改 world 的真位置**。
- **候选差异 2**：`present()` 在 `world.look/dayPart` 返回真实世界，独立氛围态的用户自选天气/时段尚未作为单独的 `visualWeather/visualDayPart` 投影。灰盒仅用 `snap.frozen` 改窗色色块。下一步最好由**只读 G2 表现层**补“真实世界 vs 氛围演出”的展示来源标签，不要污染天气生成算法。
- `game/src/app/scene.ts` 的 `SCENE_W=960` 是为了把「屋内／院子／屋边」按**调试区域横向摆放**，其 `SPOT` 与 `CROP` **不能直接复制到 05 480×270 的高品质屋内坐标**。应以 05 clean plate 上真实绘制的家具锚点为准，再在 06 里提供可转换的场景位置表。

### 第一条应当打通的竖切体验

仅用 `present()` 一份 Snapshot：屋里真实读书 → 在木屋里画出角色和一本打开的书 → 角色去泉屋后切成空镜（雪继续下，窗台和炉火依实际状态）→ 回屋时正确换回衣着/位置 → 单独打开「看看今天」展示真实已发生事件。不用在这一条里实现全部户外动物、年册或复杂天气贴图。
