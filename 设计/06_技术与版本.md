## 1. 为什么现在允许做灰盒

02/03 已定稿，04 的 U1–U6 已确认，05 可先推进视觉资产。继续只写概念文档无法实证以下问题：

- 默认雪窗小窗和完整全景里，人物分别在**真实正常生活的醒着时间**出现多少？
- 真实陪伴运行 **2–4 小时**后，会产生几件可以在场景里自然看见的**真实事件**？
- 基础生存/修缮是否能在非用户干预下自动推进，且角色有正常闲暇与活动连续性？
- 专注计时、45 分钟冷却、现实午夜、休眠/退出/异常断档是否真实正确？
- 氛围冻结、户外地图/背包/手记暂停、户外临时专注与返回原地是否不产生经济或计时漏洞？

以上由真实世界灰盒回答；**图片原型回答不了**，所以 06 可以先开始。

## 2. 灰盒边界和可复用架构

第一阶段的“灰盒”可以很丑：色块/文字/简单网格显示**人在哪里、做什么、正在什么世界时段、柴粮、项目、事件**，只要按 02 真实运行。**不能把 04/05 的概念 HTML 复制进游戏引擎假装完成**。

建议将核心分为以下可替换的层次（接口先于框架）：

| 层 | 需要维护的事实 | 能否被 UI 改写 |
|---|---|---|
| RealFocusClock | 会话、真实时间戳、有效时长、休息、暂停、任务备注、奖励冷却与现实日期份数 | 只能按 02 允许的操作修改 |
| WorldClock | 世界季节/世界日/游戏分钟、四状态转换、睡眠/醒来/天气生成 | 不能因 UI 渲染循环或切镜头修改 |
| ActorScheduler | 唯一真实位置、当前动作/阶段、生活需求、独立习惯/项目意向、行动占用与收尾 | 用户仅给有限意向 |
| ResourcesAndProjects | 木柴粮食、食材、工时阶段、储备和装备、真实出门与返家交易 | 与用户份数严格隔离 |
| WorldEventLog | 已发生的世界事件、次日小结、年册、项目变化/可见物件 | 只由真实模拟事件产生 |
| ViewPresenter | 全景、小窗、雪窗/炉边镜头、近况卡、氛围预览、可见位置统计 | **纯只读投影**，不触发模拟结算 |
| UIState | 面板开关、镜头偏好、小窗布局、通知设置、弹出近况卡 | 不改变真实世界事实 |

**核心技术底线**：渲染掉帧、窗口缩放或切到后台不能让游戏世界因为画面更新次数不同而多/少走时间；多窗口共享**同一**游戏和现实专注事实源，不可重复发份。

## 3. 最小灰盒阶段

### G0：可复现的纯逻辑核心

- 固定种子模拟：世界钟、季节天气、角色作息、柴粮、必要补给、基础项目与手记事件；先能无头运行与存档恢复，不依赖美术。
- 专注时钟：基于真实单调时间/校验后的时间戳，区分运行中、暂停、真实休眠、关闭、无法核实断档；现实 `00:00` 按日期账本重置份数，不破坏跨日累计、冷却和同一会话。
- 切换四种世界状态，另有**户外打开信息面板的临时世界暂停**，它不是有效专注，不能发份。
- 只提供白名单命令接口；不实现「给角色添柴、立刻做饭、消耗一份修缮」。

### G1：能看的真实灰盒

- 一屏：世界日/季节/天气、真实位置、当前动作、生活需求、柴粮、已完成/待办项目、世界事件。
- 一个 **320×180 / 480×270** 紧凑视图的矩形占位：标出窗、桌、人物与真实镜头可视框，统计 `actorVisibleInWindow`；另一个全景统计 `actorVisibleInWide`。
- 真实回访入口：当前真实场景痕迹、近况卡、完整手记。不能由 UI 虚构「今天发生过」的工程或活动。
- 独立进程/标签的多窗口共享状态、后台/休眠测试优先，但系统级置顶仅作为可验证能力，不提前承诺 Chrome/Safari 全支持。

### G2：状态与美术接合

- GPT 交付同一母场景分层、美术位置及状态映射；Claude 以 `sceneState` + `actorState` 驱动，不要求重写模拟核心。
- UI 视觉从 04 v1.3/05 v0.2 替换灰盒看板；暂不制作远行、霜兽、全部 24 件样式或三张完整野外地图。
- 首个可玩版优先验证 **松林一次可往返探索**，基本生活不依赖玩家探索；其他两张区域属于后续范围。

## 4. 必须记录但不必对用户显示的指标

| 指标 | 建议记录方式 | 用来回答 |
|---|---|---|
| 人物可见率 | 按正常伴随运行的游戏时间和角色位置 + 实际镜头裁切判断，分别统计「醒着的时间里在雪窗/全景可见」 | A1/A4 的真实价值 |
| 生活事件数 | 记录每次真实做饭、提水、读书、修缮阶段、取物与闲暇；与场景可见痕迹关联 | 回访是不是只能看到空房 |
| 自主行为配比 | 各工作、必要生活、观测、闲暇、睡眠时间的分布 | 是否变成全天施工的机器人 |
| 资源稳定性 | 按季节记录柴粮、俭/正常/丰足及实际缺口，包含出门扣账 | 脚本推演能否迁移 |
| 计时可靠性 | 模拟/实测跨日、后台、休眠、退出、时钟校正与未知断档；同一会话不重复领奖 | 02 奖励实装可信度 |
| 冻结可靠性 | 进入氛围、户外临时专注、户外读背包/地图后的资源与世界时间差 | 暂停时是否暗中结算 |

**不要直接设一个“必须看见人物 80%”的指标**来反向扭曲生活行为；先记录真实数据，再由用户判断陪伴感。

## 8. 技术选型和项目结构（v0.2）

| 项 | 选了什么 | 理由 |
|---|---|---|
| 语言 | TypeScript，严格模式 | 状态多、规则细，要靠类型兜住；以后 Web 和桌面壳共用一份内核 |
| 内核的依赖 | 没有。不碰 DOM，不读系统时钟，随机数用存得下来的种子 | 无头长跑、测试、以后搬进桌面壳都不用改 |
| 界面 | 灰盒阶段不用框架，原生 DOM 和 Canvas | 界面要整个换掉，现在引框架是白引 |
| 构建和测试 | Vite、Vitest；工具脚本直接用 Node 跑 `.ts` | 开发依赖只有 `typescript`、`vite`、`vitest`、`@types/node` 四个 |
| 桌面版 | 还没选。内核不依赖浏览器，Tauri 或 Electron 都接得上 | 等 Web 验证完再定；菜单栏、置顶小窗、休眠通知这些要原生能力 |

目录（细目见 `game/README.md`）：

```
game/
  src/core/   内核。config（数值）、content（内容表）、state、sim（世界）、outing、focus（专注和份）、
              heartbeat（时间判定）、game（四种状态和命令）、view（只读投影）、cameras、telemetry、save、longrun
  src/app/    灰盒界面。runtime（心跳、存档、多窗口）、scene（色块场景）、main（面板）
  tests/      自动化测试
  tools/      longrun（长跑）、sample（动作流水）、report（指标）
```

第 2 节的七层对应到代码：

| 第 2 节的层 | 代码 | 说明 |
|---|---|---|
| RealFocusClock | `focus.ts` | 会话、有效时间、份、日期账本、任务、成就。时间由调用方传进来 |
| WorldClock | `sim.ts` 的 `stepMinute`、`game.ts` 的 `advance` | 世界一步一个游戏分钟；走几步只看确认在运行的现实时间和当前倍率 |
| ActorScheduler | `sim.ts` 的 `decide` | 02 第 6.2 节的优先级表，一件做完定下一件 |
| ResourcesAndProjects | `sim.ts`、`outing.ts` | 柴粮、炉火、项目、菜地、行囊 |
| WorldEventLog | `state.ts` 的 `events`、`summaries`、`yearbook` | 只在真实动作做完时写入 |
| ViewPresenter | `view.ts` 的 `present` | 纯函数，测试里验证读多少次都不改状态 |
| UIState | `src/app/` 里的局部变量 | 面板开关之类，不进存档 |

**界面和内核之间只有两样东西**：`game.ts` 里 `cmd` 开头的命令（白名单，里面没有添柴、做饭、备柴、备粮），和 `present()`。接正式美术时换的是 `src/app/`。

## 9. 时间：怎么保证不多算也不少算

- **内核不读时钟。** 驱动每次心跳告诉它两件事：现在的墙上钟，和「从上次心跳到现在，确认应用在运行的毫秒数」。
- **世界走多少只看这个毫秒数。** 用整数累加（毫秒 × 倍率，满 60000 进一个游戏分钟），同样长的一段时间不管拆成多少次心跳喂进来，世界走到的地方一模一样。测试里拿 250 毫秒到 30 分钟的五种心跳间隔比过。画面刷新不参与。
- **专注在准确的时刻结算。** 一段时间里会在阶段走完、午夜、冷却到点、攒满 10 分钟这几个时刻切开，份发在那一刻，和心跳多密无关。后台被节流成一分钟一跳也一样准。
- **判定一段时间算不算数**（`heartbeat.ts`）。驱动每次心跳读两个钟：墙上钟（`Date.now`，休眠时照走）和单调钟（`performance.now`）。

| 两次心跳之间 | 判为 | 处理 |
|---|---|---|
| 单调钟走了不到 120 秒，两个钟对得上 | 确认在运行 | 照常记进专注和世界 |
| 墙上钟比单调钟多走了 30 秒以上 | 休眠（或时钟被往后拨） | 不计、不补；专注停在「已暂停」，不给选择 |
| 两个钟都走了超过 120 秒 | 确认不了的断档（页面被挂起、冻结） | 世界不补；专注停在「已暂停」，给「算进去 / 不算」 |
| 墙上钟往回走 | 时钟被往回拨 | 以单调钟为准；份的冷却从这一刻重新计 45 分钟；每日份数按日期查表，不会多给 |
| 重新打开应用 | 退出过 | 从存档接着走，离开多久都不补；专注停在「已暂停」，不给选择 |

单调钟在休眠时走不走，各浏览器不一样。不走的，休眠落在第二行；走的，落在第三行，变成问你一句。两种都不会把休眠悄悄算成专注。阈值在 `config.ts` 的 `heartbeat` 里。

## 10. 存档和多窗口

- **存档**是整局游戏的一份 JSON（世界、专注、当前状态、指标），带版本号。现在放在浏览器的 `localStorage`，每 10 秒、每次操作后、页面转到后台和关闭时各存一次。读到更新版本的存档会拒绝，不会当成坏档覆盖。存档结构以后改了，在 `save.ts` 里按版本迁移。
- **世界停住时存档不变**，所以「关掉再开」和「一直没关」在世界这一侧走出来的结果一样，测试里比过。
- **多窗口**：同一时间只有一个窗口（主窗口）在推进游戏，靠浏览器的 Web Locks 抢一把锁。其余窗口只显示主窗口广播的状态，操作发给主窗口执行。主窗口关了，排队的窗口接手，从它最后广播的状态接着走。所以开第二个窗口不会让世界算两遍，也不会多发份。
- 事件逐条保留最近 12 个游戏日，更早的只留每日小结和年册的计数，存档不会一直变大。

## 12. G1 还要在真机上验证的
